## Bounded experiment scope and evidence rules

The default learning batch is **seven runs**: three methods (QSGD, fixed p=1,
adaptive) for seeds 42 and 43, plus fixed p=0 once for seed 42. This is a target
scope, not a guaranteed runtime. At most one additional development-policy run
is permitted only if the predeclared development rule and compute cap allow it.
Freeze its selection procedure before looking at confirmation results. Do not
add a broad budget sweep or three-seed/five-method matrix by default.

Existing completed runs may replace a planned run only when source, parameters,
data/model/initialization, measurement boundary and execution environment match
the new protocol. The old Windows pilot is historical context, not a matched
WSL control. Linux controls must be generated when there is no compatible saved
run. The already passed codec checks are reused unless relevant code changes.

The seed-42 batch is development evidence if it informs budget choice; seed 43
is confirmation for the frozen policy. Two seeds are limited evidence, not a
basis for a broad statistical-superiority or equivalence claim. Keep checkpoint
selection by validation loss and the held-out test unused in this planned phase.

## Working blocks and stop rules

Organize active work into 40-60 minute units: one protocol/design decision,
one implementation/check, one analysis/figure, or one writing/demo segment.
Training duration is separate and machine-dependent. Reuse available evidence
instead of repeating successful tests. Do not create an automation without an
explicit scheduling request.

Check client concurrency against the 8 GB WSL cap before launch. Run methods
sequentially; do not launch a new batch while a prior one still occupies the
budget. If the development result fails the frozen criterion, either use the
single permitted revision or report it; do not spend the confirmation seed on
repeated policy selection. If runs slip, preserve PDF sharing and Monday's
meeting package, omit the optional exercise and show honest partial results.

Each result summary should relate the observed trade-off to a relevant source
and its assumptions. Reuse the verified literature notes; a fresh broad search
after every run is unnecessary. Keep R3's access gap and ASCEND's unresolved
proof reference labeled if they appear in the slides.
